## Findings

### [A] `ActionState.Failed` was dead code, and its field broke storage packing — **Fixed**

**Location:** `src/Powers.sol::fulfill()`, `src/interfaces/PowersTypes.sol::Action`/`ActionState`

**Description:** In `fulfill()`, a failed external call set `action.failedAt = uint48(block.number)` and then unconditionally reverted (either bubbling up the sub-call's revert reason via inline assembly, or reverting with `Powers__MandateFulfillCallFailed()`). Because Solidity reverts undo all state changes made within the reverting call frame, and `fulfill()` is invoked via a plain external call with no surrounding `try/catch`, the `failedAt` write was always rolled back. Confirmed by repo-wide grep: `ActionState.Failed` was referenced in exactly one place — its own `return` statement in `getActionState()` — with zero writers anywhere that could ever make it observable, and zero readers in tests, mandates, or the frontend.

A secondary, previously undocumented consequence: `failedAt` (a 6th `uint48` field) pushed the `Action` struct's first packed slot from 240 bits to 304 bits, which exceeds one 256-bit storage slot. Solidity's automatic layout therefore split `voteStart`/`mandateId` into a second, mostly-empty slot — meaning **every** `propose()`/`request()` call was paying for an extra cold/warm `SSTORE` purely as a side effect of a field that could never be legitimately read.

**Impact:** Functional impact is low (the "failed" state was simply unreachable, not exploitable), but it is a genuine correctness bug relative to the documented state machine (`PowersTypes.sol`'s enum comments explicitly say `// - 8: log this`, implying it should be observable), and the packing regression had a real, measurable gas cost on every governance action.

**Fix applied:**
- Removed `uint48 failedAt;` from `PowersTypes.Action` (restores the original 6-field / 256-bit packing of `proposedAt, requestedAt, fulfilledAt, cancelledAt, voteStart, mandateId` into a single slot).
- Removed `Failed` from the `ActionState` enum (safe — it was the last value, so no other enum ordinal shifts, and grep confirmed zero external dependents in `src/`, `test/`, or `frontend/`).
- Removed the dead `action.failedAt = ...` write and the `if (action.failedAt > 0) return ActionState.Failed;` branch in `getActionState()`.
- Left a comment at the call site explaining that a failed call reverts the whole transaction, so no separate "failed" state is ever persisted — the action simply remains un-fulfilled (ties into finding C).

### [B] `ActionState.Proposed` was unreachable — and the frontend was silently relying on it — **Fixed (frontend)**

**Location:** `src/Powers.sol::getActionState()`, `frontend/hooks/useChecks.ts:177`

**Description:** `getActionState()` computes `voteStart`/`deadline` unconditionally the instant `proposedAt > 0`, and immediately falls through to the `Active`/`Defeated`/`Succeeded` branch. There is no code path — under any `Conditions` configuration — that returns `ActionState.Proposed` (enum value `1`). Confirmed by grep: `ActionState.Proposed` appears nowhere in `src/`, `test/`, or `governance/`.

Critically, this is not just a theoretical dead-code issue: `frontend/hooks/useChecks.ts` computed its `voteActive` indicator as `mandate.conditions.quorum == 0n ? true : actionState == 1n` — i.e. it checked for exactly the unreachable value. Since `getActionState()` can never return `1` for a quorum-gated mandate, **`voteActive` was permanently `false` for every mandate that actually requires a vote**, for as long as this code has existed. The correct state to check is `ActionState.Active` (enum value `3`), which is what `getActionState()` genuinely returns during the voting window.

**Impact:** This is a real, currently-shipping dApp bug, not just a cosmetic Solidity issue — any UI surface relying on `checks.voteActive` would have misrepresented whether a proposal's voting window was actually open.

**Fix applied:**
- `frontend/hooks/useChecks.ts`: changed `actionState == 1n` to `actionState == 3n`, with a comment recording both the correct enum value and why `Proposed` (1) can never be returned.
- **Solidity left unchanged (deliberately):** unlike `Failed`, `Proposed` sits in the *middle* of the enum (index 1 of 9 at the time of review). Removing it would shift every subsequent value's ordinal (`Cancelled` 2→1, `Active` 3→2, ... `Fulfilled` 7→6), which would silently break several *other* hardcoded numeric comparisons already present in the frontend (`useChecks.ts:171-174` compares against `5n/6n/7n`; `usePowers.ts:471` compares against `2,4,7`). Reordering the enum to "clean up" `Proposed` would trade one bug for several new ones unless every one of those call sites is updated in lockstep. Given the actual reported bug is fully fixed by the frontend correction above, I chose the lower-risk path: document `Proposed` as currently unreachable directly in the enum (see `PowersTypes.sol`), rather than risk a wider renumbering. **Recommendation:** if the team wants to fully retire `Proposed`, do it as a dedicated, reviewed change that greps and updates every hardcoded `ActionState` ordinal in `frontend/` first — do not do it opportunistically alongside unrelated work.

### [C] Stuck `quorum==0` + async-mandate actions have no on-chain recovery path — **Fixed**

**Location:** `src/Powers.sol::cancel()`, `src/AsyncMandate.sol`

**Description:** `cancel()` required `action.proposedAt > 0` (`Powers__ActionNotProposed()` otherwise) but did not check `requestedAt`. This means a *voted* action stuck mid-`request()` (e.g. an async mandate whose oracle never calls back) could still be cancelled by the original proposer at any time before fulfillment — a reasonable safety net. But a mandate configured with `quorum == 0` — a common, intentional pattern for direct, non-voted actions — never sets `proposedAt` (only `propose()` sets it; `request()` does not). If *that* kind of action got stuck (e.g. a `quorum==0` mandate built on `AsyncMandate` whose oracle fails or never responds — see also the `ChainlinkFunctions_Open` oracle-failure gap noted in the earlier mandate-level review this session), there was no recovery path through `Powers.sol` at all. The action would be permanently `Requested`.

**Impact:** Liveness/DoS on a specific class of action (direct + async), not a fund-loss vector, but worth fixing rather than leaving as an accidental gap.

**Fix applied:** `cancel()`'s existence check now reads `if (action.proposedAt == 0 && action.requestedAt == 0) revert Powers__ActionNotProposed();` — recognizing actions created via either `propose()` or `request()`. All other checks (caller must be `action.caller`; `fulfilledAt`/`cancelledAt` must both be zero) are unchanged. This is safe against a late oracle callback racing a cancellation: `fulfill()` already reverts with `Powers__ActionNotRequested` if `action.cancelledAt > 0` (pre-existing check), so a callback arriving after cancellation is a clean no-op revert, not a double-execution risk.

New test coverage: `test/unit/AsyncMandate.t.sol::AsyncMandateFlowTest::testCancelRecoversStuckAsyncAction` (a `quorum==0` async action stuck in `Requested` can now be cancelled by its original caller) and `testLateOracleCallbackRevertsAfterCancellation` (a late callback after cancellation reverts cleanly). `test/unit/Powers.t.sol::CancelTest::testCancelRevertsIfActionNotProposedOrRequested` and `testCancelRevertsIfDirectRequestActionAlreadyFulfilled` updated/added to cover the new existence-check semantics on both the true-nonexistent and synchronous-direct-request paths. Full suite: 689 tests passed, 0 failed, 7 skipped (pre-existing skips).

### [D] Reentrancy-adjacent throttle-bypass window in `fulfill()` — **Fixed**

**Location:** `src/Powers.sol::fulfill()`

**Description:** `fulfill()` correctly sets `action.fulfilledAt` *before* the loop of external calls (proper checks-effects-interactions — prevents the same action being fulfilled twice via reentrancy). However, `mandate.latestFulfillment = uint48(block.number)` — the value `Checks.check()` uses to enforce `Conditions.throttleExecution` — was only written **after** the loop completed. If one of the external calls made during that loop reentered `Powers.request()` for the *same* `mandateId` (a different `actionId`/nonce), the throttle check inside `Checks.check()` would read the *stale*, pre-fulfillment `latestFulfillment` value and could pass prematurely, bypassing the intended minimum-gap-between-executions guarantee for that mandate.

**Impact:** Conditional — required (a) a target contract within the call batch capable of reentering (e.g. an ERC721/1155 `safeTransfer` callback, or a Safe/treasury call with a callback hook), and (b) the reentrant caller holding `allowedRole` for the same mandate. Not a guaranteed universal exploit, but a real gap, since throttled mandates are specifically the ones a governance designer expects to have hard rate limits on.

**Fix applied:** Moved the `mandate.latestFulfillment = uint48(block.number);` write to immediately after `action.fulfilledAt` is set, before the external-call loop — mirroring the existing `fulfilledAt` checks-effects-interactions pattern. The now-redundant write at the end of the function was removed. `forge build` passes; the full Solidity suite (678 tests, including `PowersUtilities.t.sol`'s throttle-specific tests: `testcheckWithThrottleExecutionGapTooSmall`, `testcheckWithThrottleExecutionGapSufficient`, `testcheckWithThrottleExecutionExactlyAtThreshold`) passes with 0 failures.

### [E] Stale comment above an active `emit` — **Fixed**

**Location:** `src/Powers.sol`, immediately above `emit ActionFulfilled(...)` in `fulfill()`

**Description:** The comment read `// emit event. -- commented out to save gas, can be re-enabled if needed.` directly above an emit statement that was **not** commented out — it was live, active code. Low severity on its own, but the kind of drift that could mislead a future maintainer into either believing gas was saved when it wasn't, or "helpfully" re-enabling something already enabled (creating a duplicate-emit bug).

**Fix applied:** Comment removed manually by 7Cedars (not part of the automated fixes in this review).

### [F] No Powers-native emergency pause — Open (by design)

**Description:** Every state-mutating admin function (`adoptMandate`, `revokeMandate`, `assignRole`, `revokeRole`, `editFlowByIndex`, `addFlow`, `removeFlow`, `labelRole`, `blacklistAddress`, `setTreasury`, `setPaymaster`) is `onlyPowers`-gated (self-call only). An emergency pause is itself just a mandate (`Pause_Mandates`, in `src/mandates/reform/`) — so any org that never adopts a pause-capable mandate has no fast-response mechanism against a malfunctioning or compromised mandate beyond whatever (possibly slow/timelocked) governance process is already configured. This is consistent with the protocol's stated minimal-core philosophy and is very likely an intentional tradeoff (see the existing `260326_chain-defenders` pre-audit exchange, where the team confirms immutability-as-a-feature is intentional for orgs that choose it) — flagged here as a reminder to make explicit to governance designers, not as a bug.

### [G] Vote approves intent, not pinned execution content — Partially addressed

**Location:** `src/Powers.sol::propose()` / `request()`, cross-referenced against state-dependent mandates (`PeerSelect`, `DelegateTokenSelect`, `RevokeInactiveAccounts`, `ElectionRegistry_Tally`, the `GatedAccess` family)

**Description:** `propose()` and voting only fix `mandateId + mandateCalldata + nonce` (via `actionId = keccak256(abi.encode(...))`). The actual `targets[]/values[]/calldatas[]` that get executed are computed **fresh, at `request()` time**, by the mandate's `handleRequest`, reading whatever chain state exists at that moment — which can be materially later than when the vote concluded, since nothing forces immediate execution after `Succeeded`. For deterministic mandates (`PresetActions`, `OpenAction`) this is a non-issue. But for any mandate whose `handleRequest` reads live, externally-influenceable state, voters are implicitly approving "run this logic against whatever state exists whenever someone gets around to calling `request()`" — not a fixed, previewed outcome. An adversary able to influence that state before `request()` is called (front-running the execution transaction, or simply waiting for favorable conditions) can change what actually executes without a new vote ever being cast.

**Impact:** Architecturally sound as a tradeoff (the alternative — snapshotting all relevant state at propose-time — has its own significant costs and isn't generally applicable across arbitrary mandate logic), but represents a real, non-obvious gap between "what was voted on" and "what happens" for a meaningful subset of shipped mandates.

**Recommendation:** Document this explicitly for mandate authors (a good candidate addition to `/create-mandate`'s Phase 3 gotcha checklist, or to `Checks.sol`'s NatSpec), and consider whether high-stakes mandates in this category should add their own freshness/staleness guards (e.g., a maximum-age check on the state they read) rather than relying on immediate execution as an informal mitigation.

**Fix applied (follow-up session, 2026-07-03):**
- Documentation: added NatSpec to `PowersTypes.Conditions` and `Checks.sol::check()` explaining the vote-to-execution gap, and a new gotcha item (#6) to `/create-mandate`'s Phase 3 checklist directing authors of state-reading mandates to consider `maxExecutionDelay`.
- Protocol: added an opt-in `uint32 maxExecutionDelay` field to `Conditions` (fits the existing packed slot — 176 of 256 bits now used, no new storage slot). For quorum-gated mandates, `Checks.check()` now reverts with `Checks__ExecutionWindowExpired` if `request()` is called more than `maxExecutionDelay` blocks after `voteStart + voteDuration` (i.e., after the vote succeeded). Default `0` disables the check, preserving today's unbounded-wait behavior for every existing mandate/org — this is opt-in per mandate, not a protocol-wide requirement. No effect on `quorum == 0` direct actions, which execute atomically within a single `request()` call and have no vote-to-execution gap to bound.
- This narrows, but does not eliminate, the gap: it bounds *how long* state can drift after a vote succeeds, but does not pin the specific execution payload the way full state-snapshotting at propose-time would. Mandates with especially high stakes may still want their own snapshot-based guard (see the "avenue C" note this recommendation always implied) on top of this coarser, block-count-based bound.
- New test coverage: `test/unit/PowersUtilities.t.sol::ChecksTest::testcheckWithMaxExecutionDelayRevertsAfterWindowExpires`, `testcheckWithMaxExecutionDelayPassesWithinWindow`, `testcheckWithZeroMaxExecutionDelayNeverExpires`. Full suite: 692 tests passed, 0 failed, 7 skipped (689 pre-existing + 3 new).
- Struct-literal call sites requiring the new named field were updated: `test/unit/Powers.t.sol`, `test/TestConstitutions.sol` (3 occurrences), `src/mandates/integrations/ElectionRegistry/ElectionRegistry_CreateVoteMandate.sol`, `src/mandates/integrations/SlateRegistry/SlateRegistry_AddSlate.sol`. Governance deploy scripts under `governance/` construct `Conditions` via a persistent zero-initialized struct with individual field assignment, not named-field literals, so they were unaffected and default to `maxExecutionDelay = 0` automatically.

### [H] Oversized return data silently truncated — Open

**Location:** `src/Powers.sol::fulfill()`

**Description:** `if (returndata.length <= MAX_RETURN_DATA_LENGTH) { action.returnDatas.push(returndata); } else { action.returnDatas.push(abi.encode(0)); }` — a call whose return data exceeds the configured cap is silently replaced with `abi.encode(0)` rather than reverting. Several "on-return-value" mandates (`BespokeAction_OnReturnValue`, `PowersFactory_AssignRole`, etc., per the earlier mandate-level review) trust `getActionReturnData` without independently validating its shape — such a mandate would silently receive `abi.encode(0)` instead of an explicit failure signal if the parent call's return data happened to exceed the cap.

**Recommendation:** Consider reverting instead of silently truncating, or at minimum documenting this behavior prominently for anyone writing a return-value-chaining mandate.

## Additional Informational Notes

- **No on-chain verification of mandate behavior at adoption time — partially addressed.** `constitute()`/`adoptMandate()` originally accepted a raw `address targetMandate` with no verification beyond an ERC165 `IMandate` interface check (`PowersUtilities.storeMandate`). A malicious or buggy mandate with an innocuous `nameDescription` was trusted identically to a well-audited one.

  **Fix applied:** `Powers.sol` now has an immutable `MANDATE_REGISTRY` address, set at deploy time and enforced inside the shared `_storeMandate`/`PowersUtilities.storeMandate` path (covering both genesis `constitute()` and post-genesis `adoptMandate()`). If `MANDATE_REGISTRY != address(0)`, any mandate address not currently active in that `MandateRegistry` instance is rejected with a new `Powers__MandateNotRegistered` error. `address(0)` preserves today's fully permissionless behavior — this is an opt-in guarantee per org, not a protocol-wide mandate.

  This required extending `MandateRegistry.sol` itself with a new `isMandateAddressActive(address)` lookup (an `address → (name, version)` reverse index populated at registration time), since the registry previously had no way to answer "is this address registered" without already knowing its name and version — which `Powers.sol` doesn't have at adoption time and (by explicit design choice) deliberately does not check. `PowersDeployer.sol` and `PowersFactory.sol` were updated to thread this parameter through; **already-deployed registries on Ethereum Sepolia and Arbitrum Sepolia do not have this new lookup and must be redeployed (with all catalogue mandates re-registered) before this feature can be used on those networks** — a one-time operational step tracked separately from this code change.

  **What this does *not* address**: version pinning (a deliberate scope decision — checking only registry *membership*, not a specific `MAJOR.MINOR.PATCH`, was chosen as sufficient for now); retroactive protection for mandates already adopted by an existing org before its registry deactivates them; and the deeper question of whether a registered mandate's code is actually *correct* — the registry is a curated allowlist, not a formal verification mechanism. **The core recommendation stands**: review the adopted mandates, not just the core — this change narrows *who* can be adopted to a curated set, it does not audit them for you.

  New test coverage: `test/unit/PowersMandateRegistry.t.sol` (8 tests — registered/unregistered/deactivated/reactivated/zero-address-opt-out, across both `constitute()` and `adoptMandate()`).
- **`EIP712` is inherited by `Powers.sol` and its constructor is invoked (`EIP712(name_, version())`), but `_hashTypedDataV4`/domain-separator functionality is never called anywhere else in `src/`** (confirmed by grep). This adds bytecode size and minor deploy-time gas for currently-unused functionality — either dead weight worth pruning, or a signal of planned-but-unshipped signature-based meta-governance (plausible given the `PowersPaymaster` ERC-4337 gasless-UX investment elsewhere in the repo) that should be documented either way.
- **`computeActionId`'s formula (`keccak256(abi.encode(mandateId, mandateCalldata, nonce))`) is implemented independently in both `Checks.sol` (`public pure`) and `MandateUtilities.sol` (`internal pure`)**. Both are correct today, but a future change to one without the other would silently desync Powers' own gating logic (`Checks.check()`) from every mandate's own `handleRequest` computation. Low risk, but worth consolidating into a single source of truth.

## Strengths Worth Noting

- The single `propose → [vote] → request → fulfill` pipeline that *everything* — including the org's own admin operations — is forced through is a genuinely elegant unifying design: there is exactly one way anything happens, which makes the protocol both learnable and trivially composable.
- `PowersTypes.Action`/`Conditions` storage packing is deliberate and, after this review's fix, correctly restored — the struct definitions carry explicit slot-packing comments and the field ordering matches them.
- `PowersUtilities.setRole` proactively guards against a subtle quorum-math footgun: adopting a mandate with `allowedRole == PUBLIC_ROLE` and `quorum > 0` is explicitly disallowed (`Powers__VoteWithPublicRoleDisallowed`), preventing a scenario where quorum would trivially always pass at zero votes cast (since nobody is ever literally enrolled in the `PUBLIC_ROLE` members array).
- Zero-address, self-address, and public-role guards for role assignment live once, centrally, in `PowersUtilities.setRole` — every mandate that emits an `assignRole`/`revokeRole` call gets this protection for free.
- Real, sustained investment in test infrastructure (`testing-principles.md`, category-specific `TestSetup*` base classes, per-mandate and per-helper test files, a dedicated coverage-analysis skill) — differentiates this codebase from typical fast-moving DAO tooling.
