# Powers Protocol — Security Audit

**Auditor:** Claude Fable 5 (Fable refused, executed Opes 4.8)
**Date:** 2026-07-03
**Target version:** Powers `v0.6.1`
**Commit / branch:** `c4e5bbf` on `develop`
**Compiler:** solc 0.8.30, optimizer 600 runs, EVM `cancun`
**Verification:** `forge build` (clean) and the core unit suite (`test/unit/Powers.t.sol`, 129 tests) run green as a baseline.

> This audit was performed independently, without reference to the other reports in `solidity/audits/`. Findings are derived from source only.

---

## 1. Summary

Powers is a modular, role-based governance protocol. A single non-upgradeable engine (`Powers.sol`) owns all state — roles, adopted mandates, actions, treasury pointer — and every governance action flows through it as a lifecycle: `propose → castVote → request → (mandate) → fulfill`. All *logic* lives in external **mandate** contracts, which are trusted, role-restricted transformers that turn caller input into `(targets, values, calldatas)` for the engine to execute.

The core is small, careful, and shows evidence of prior hardening (the reentrancy-ordering comment in `fulfill`, the `maxExecutionDelay` option, the `MANDATE_REGISTRY` allow-list). No memory-safety, arithmetic-overflow, or classic reentrancy vulnerability was found in the core engine. The most significant issues are **governance-integrity** issues that arise from the protocol's central design choice: **votes are validated against live on-chain state at execution time, not against a snapshot taken when voting opened.**

### Findings

| ID | Severity | Title |

Severity = impact × likelihood. **Critical**: direct loss/seizure, easy to trigger. **High**: governance integrity or funds at risk under realistic configuration. **Medium**: exploitable under specific-but-common configuration, or requires a privileged-but-not-trusted actor. **Low**: limited impact or narrow precondition. **Informational**: no direct security impact; hardening / documentation.

## 2. Architecture

### 2.1 Actors and objects

- **Roles** (`PowersTypes.Role`) — a role is an id (`uint256`) with a set of member addresses and a per-member `since` block. Two are reserved: `ADMIN_ROLE = 0` and `PUBLIC_ROLE = type(uint256).max` (everyone). Voting is **one-account-one-vote**: a role's power is its member count, so votes are `uint32` counts, not token weights.
- **Mandates** (`Mandate` / `AsyncMandate`) — external contracts adopted into the engine with a `Conditions` struct (`allowedRole`, `quorum`, `succeedAt`, `votingPeriod`, `timelock`, `throttleExecution`, `needFulfilled`, `needNotFulfilled`, `maxExecutionDelay`). A mandate's `handleRequest()` is a **view** function returning the calls to execute. Mandates are *privileged*: whatever calls they return are executed by the engine with the engine's own authority.
- **Actions** (`PowersTypes.Action`) — one governance request, keyed by `actionId = keccak256(mandateId, mandateCalldata, nonce)`. Its lifecycle timestamps (`proposedAt`, `requestedAt`, `fulfilledAt`, `cancelledAt`) plus vote tallies define its state.
- **Flows** — human/UI-readable ordered lists of mandate ids; purely descriptive, but some reform mandates (`Pause_Mandates`, `SlateRegistry_AddSlate`) read/edit them to locate mandates by position.

### 2.2 Lifecycle

```
constitute() ── admin loads initial mandates ──► closeConstitute() [one-way]
     │
     ▼
propose(mandateId, calldata, nonce)          ── only if quorum>0; opens a vote
     │  castVote / castVoteWithReason         ── members of allowedRole, 1 vote each
     ▼
request(mandateId, calldata, nonce)          ── Checks.check(): parent deps, throttle,
     │                                            quorum→Succeeded, timelock, exec window
     │  IMandate.executeMandate(...)          ── engine calls the mandate
     │     handleRequest() [view] → calls     ── mandate computes (targets,values,calldatas)
     ▼
fulfill(mandateId, actionId, targets,values,calldatas)   ── ONLY the target mandate may call
        └─ loops targets[i].call{value}(calldatas[i])     ── engine executes with its authority
```

For `quorum == 0` mandates there is no vote: `request()` runs the checks and executes atomically in one transaction. For `quorum > 0` mandates, `propose()` opens a vote, members vote, and after the deadline `request()` may be called if the action resolved to `Succeeded`.

**Async** mandates (`AsyncMandate`) replace the direct `fulfill` with `_callOracle(...)`, expecting an off-chain/oracle callback to later invoke `_replyPowers → fulfill`. The async base is a scaffold; the callback and oracle wiring are the concrete subclass's responsibility (none of the Tier 0–3 set uses it).

### 2.3 Trust boundaries

1. **Engine (`Powers.sol`) = fully trusted, immutable.** It cannot be upgraded; all state-changing admin functions (`adoptMandate`, `assignRole`, `revokeMandate`, `setTreasury`, `blacklistAddress`, `addFlow`, …) are `onlyPowers` — reachable only through a mandate execution. There is no owner backdoor after `closeConstitute()`.
2. **Mandates = privileged and must be audited before adoption.** The source repeats this warning (`Powers.sol:175`, `:505`). A mandate returns arbitrary `(targets, values, calldatas)` that `fulfill` executes with only blacklist + length checks. The `MANDATE_REGISTRY` allow-list (optional, immutable per org) constrains *which addresses* can be adopted, but not what an adopted mandate does.
3. **Roles = the real access-control surface.** Because mandates are powerful, the security of a deployed org rests almost entirely on *which role gates which mandate*. Mis-gating (e.g. `OpenAction` behind `PUBLIC_ROLE`) hands the whole org to the public — this is a configuration responsibility, not a core bug, but it is the dominant risk in practice.
4. **Helper registries (`Nominees`, `ElectionRegistry`, `SlateRegistry`) are `onlyOwner`-gated**, and the owner is expected to be the Powers instance itself, so the DAO mediates all writes. `MandateRegistry` and `PowersFactory` are owned by an external operator (curator / deployer) — a trusted off-protocol party.

## 3. Core findings

### C-01 — Quorum and success thresholds use the live member count, not a vote-time snapshot — **High**

**Location:** `Powers.sol:607–630` (`_quorumReached`, `_voteSucceeded`), via `_countMembersRole` (`:646–648`); consumed by `getActionState` (`:774`) and `Checks.check` (`Checks.sol:76–95`).

`_quorumReached` and `_voteSucceeded` compute the denominator — the number of eligible voters — by reading `roles[allowedRole].membersArray.length` **at the moment state is evaluated**, while `forVotes`/`abstainVotes` are absolute counts accrued during the vote:

```solidity
uint256 amountMembers = _countMembersRole(conditions.allowedRole);   // live count
return conditions.quorum == 0
    || amountMembers * conditions.quorum <= (forVotes + abstainVotes) * DENOMINATOR;
```

There is no checkpoint of the role's size at `voteStart`. Because `getActionState` is recomputed live — including inside `request()` after the voting deadline — the outcome of a *concluded* vote can still be flipped by changing the role's membership before `request()` is called.

**Failure scenario (both directions):**
- *Defeat a passing proposal.* Org uses open membership (a `SelfSelect` mandate assigns role `R`) and gates a voting mandate on the same role `R`. A proposal is on track to pass. An adversary (or many sock-puppets) `SelfSelect` into `R`, inflating `amountMembers`. The fixed `forVotes` now fail `forVotes*100 ≥ amountMembers*succeedAt`, so the action resolves to `Defeated` and can never be `request()`ed.
- *Pass a failing proposal.* Membership can be renounced (`RenounceRole`, or any revoke path). Colluding members who intended to abstain/vote against instead renounce role `R` right before `request()`, shrinking `amountMembers` until a minority `forVotes` clears quorum and threshold, resolving `Succeeded`.

Both require only access to a membership mandate for the *voting* role — precisely the configuration the skill's default "open membership + member voting" pattern produces. The manipulation window runs until `request()` (there is no snapshot and, by default, no deadline on how long after success `request()` may be called — see C-02).

**Recommendation:** Snapshot the eligible-voter count at `voteStart` (store it on the `Action`, analogous to how OpenZeppelin Governor snapshots total supply at the proposal block) and use that stored value as the denominator in `_quorumReached`/`_voteSucceeded`. If a live count is intentional, document it prominently and steer designers away from gating votes on freely-joinable/leavable roles.

**Status:** Plausible (source-confirmed; no snapshot logic exists). A focused PoC (open a vote, mutate membership, observe `getActionState` flip) would confirm end-to-end.

### C-02 — A succeeded vote approves *intent*, not a payload; `Succeeded` actions never expire by default — **Medium**

**Location:** `Checks.check` (`Checks.sol:42–110`); `Conditions.maxExecutionDelay` (`PowersTypes.sol:27–33`); every state-reading mandate.

`Checks.check` re-validates only the *intent* tuple (`mandateId + mandateCalldata + nonce`). The actual calls are produced by `handleRequest()`, which runs **live at `request()`-time** and may read mutable state (role sets, balances, delegation, tallies) not bound by the calldata. Because a `Succeeded` action has no natural expiry, and `maxExecutionDelay` **defaults to 0 (disabled)**, the gap between "voters approved" and "state read at execution" is unbounded unless a designer opts in.

The team already documents this clearly (`PowersTypes.sol:9–16`, `Checks.sol:30–36`) — this finding assesses residual risk and argues the default is unsafe. Concrete manifestations are C-01, C-03, and C-04. Example: voters approve `SelfSelect` for account A into role `R`; nothing binds *when* it executes, so it can be held and executed much later under changed conditions.

**Recommendation:** Consider making `maxExecutionDelay` default to a sane non-zero bound for quorum-gated mandates (fail-safe rather than fail-open), or require it to be set explicitly (revert on 0) for any mandate whose `handleRequest` reads external state. At minimum, surface the risk in `/design-org` guidance so every state-reading, quorum-gated mandate ships with a `maxExecutionDelay`.

**Status:** Confirmed (behavior is by design and documented; the concern is the fail-open default).

### C-03 — `DelegateTokenSelect` ranks on live `getVotes()`, enabling delegation/flash manipulation of elections — **Medium**

**Location:** `DelegateTokenSelect.sol:94`.

The mandate ranks nominees by `ERC20Votes(votesToken).getVotes(nominee)` — the **current** voting power — read at `request()`-time:

```solidity
mem.delegatedVotes[mem.i] = ERC20Votes(mem.votesToken).getVotes(mem.nominees[mem.i]);
```

`getVotes` is instantaneous, not a historical checkpoint (`getPastVotes(account, timepoint)`). An attacker can acquire or borrow a large `ERC20Votes` balance, delegate it to a chosen nominee (or self-nominate and self-delegate) in the same block as `request()`, capture the top-N role seats, then undelegate/return the tokens. Where this mandate is a direct (`quorum == 0`) action callable by the relevant role — the pattern the skill documents — the whole selection is decided by delegation state in one block and is trivially manipulable, including via flash-loaned governance tokens.

**Recommendation:** Rank on `getPastVotes(nominee, snapshotBlock)` where `snapshotBlock` is fixed when the election/selection opens (e.g. stored in config or derived from `proposedAt`), so voting power cannot be borrowed just-in-time. The same live-read caveat applies to any future mandate reading token balances at execution.

**Status:** Confirmed (source: `getVotes`, not `getPastVotes`).

### C-04 — Nominee-set mutation griefs or redirects pending selection/election results — **Medium**

**Location:** `PeerSelect.sol:88–160`; `Nominees.sol`; analogous shape in `ElectionRegistry_Vote/_Tally`.

`PeerSelect` encodes the voter's choice as a `bool[]` whose positions map onto `Nominees.getNominees()` — but that array is read **again at execution time** (`PeerSelect.sol:89`), and its length/order can change between the vote and the `request()`:

```solidity
mem.nominees = Nominees(mem.nomineesContract).getNominees();     // live
if (mandateCalldata.length != mem.nominees.length * 32) revert("Invalid selection length.");
```

- **Griefing / DoS:** if any nominee is added or removed after the vote succeeds, the length check fails and the approved action can *never* execute. Anyone with access to the `Nominate` mandate can permanently block a pending `PeerSelect` result.
- **Outcome redirection:** the `Nominees` swap-and-pop removal (`Nominees.sol:38–46`) reorders the array. If the count is coincidentally preserved (one removed, one added), the same approved `bool[]` now selects *different addresses* at the same positions than voters saw.

This is the concrete, exploitable face of C-02 for the electoral mandates. It also affects `ElectionRegistry_Vote` (nominees re-read at `handleRequest`), though the registry pins nominations to before `startBlock`, which narrows the window there.

**Recommendation:** Bind the selection to specific nominee *addresses* (encode `address[]` the voter chose, validated against membership) rather than to positional `bool[]` over a mutable array; or snapshot the nominee list when voting opens and validate against the snapshot. Freeze nominations for the duration of any open selection over that pool.

**Status:** Plausible→Confirmed by inspection (length re-check + live `getNominees()` make both the DoS and reorder deterministic).

### C-05 — Reform mandates install child mandates with all-zero conditions (ungoverned, config-less) — **Low**

**Location:** `Adopt_Mandates.sol:52–63`; same pattern in `ElectionRegistry_CreateVoteMandate.sol:81–92` and `SlateRegistry_AddSlate.sol:130–141`.

`Adopt_Mandates` builds each `MandateInitData` with a default `Conditions` — every field zero except `allowedRole` — and `config = abi.encode()` (empty):

```solidity
conditions.allowedRole = roleIds_[i];
MandateInitData({ nameDescription: "Reform mandate", targetMandate: mandates_[i],
                  config: abi.encode(), conditions: conditions });
```

Consequences: (1) every mandate adopted through this reform path is a **direct action** (`quorum == 0`, no timelock, no throttle, no execution window) executable immediately by `allowedRole` — a reform vote to *add* capability silently also grants it ungoverned; (2) mandates that need config (any `BespokeAction*`, `PresetActions`, gating mandates, …) are adopted with **empty config**, so their first `handleRequest` reverts on decode — a foot-gun that produces a dead mandate.

Because `Adopt_Mandates` decodes `mandates_`/`roleIds_` from `mandateCalldata`, a quorum-gated reform *does* bind the adopted addresses+roles to the vote (good), but voters cannot express any conditions/config for the children.

**Recommendation:** Let the reform caller/vote supply full `Conditions` and `config` per child (encode them into the calldata), or restrict `Adopt_Mandates` to a curated, config-less mandate set and document that adopted mandates are ungoverned by default.

**Status:** Confirmed (source).

### C-06 — `fulfill` blacklist screens only direct call targets — **Low**

**Location:** `Powers.sol:384–388`.

`fulfill` reverts if any `targets[i]` is blacklisted, but a blacklisted party can still be the *beneficiary* of a call whose target is an innocuous contract — e.g. `targets[i] = USDC`, `calldatas[i] = transfer(blacklisted, amount)`. The blacklist is therefore a coarse control over *who the DAO calls*, not *who benefits*.

**Recommendation:** Document the blacklist's scope (target-only) so operators don't over-rely on it for value containment; consider decoding common transfer patterns if beneficiary-level blocking is a goal (noting it can never be complete).

**Status:** Confirmed (source).

---

### C-07 — `SafeAllowance_Transfer` truncates the amount to `uint96` — **Low**

**Location:** `SafeAllowance_Transfer.sol:90, 103`.

The transfer amount is decoded as `uint256` from caller calldata, then cast to `uint96` when building the allowance-module call:

```solidity
(mem.token, mem.amount, mem.payableTo) = abi.decode(mandateCalldata, (address, uint256, address));
... uint96(mem.amount) ...
```

An amount ≥ 2⁹⁶ wraps silently, so the executed transfer differs from the approved/intended one (e.g. a proposal to move `2⁹⁶` tokens moves `0`). The Safe Allowance Module itself uses `uint96`, so the real cap is the configured allowance; impact is a griefed/incorrect transfer rather than an overspend, but it is silent.

**Recommendation:** `require(amount <= type(uint96).max)` before casting (or use OZ `SafeCast.toUint96`).

**Status:** Confirmed (source).

### C-08 — `initializeMandate` is unrestricted — **Informational**

**Location:** `Mandate.sol:50–64`, `AsyncMandate.sol:50–64`.

`initializeMandate` is `public` and unguarded. It is, however, namespaced by `mandateHash = keccak256(msg.sender, index)` and stores `powers = msg.sender`, and `executeMandate` requires `mandates[hash].powers == msg.sender` (`Mandate.sol:76–79`). An attacker calling it uses *their own* address as `msg.sender`, so they can only write into their own namespace — they cannot overwrite the config a real Powers instance stored for `(powers, index)`, and `PowersUtilities.storeMandate` re-initializes during adoption. No exploit was found; the only writer to a given `(powers, index)` slot is that Powers contract itself.

**Recommendation:** None required for safety. Optionally emit/guard to reduce confusion, or note the namespacing invariant in NatSpec.

**Status:** Confirmed benign (source).

### C-09 — Decode-robustness and encoding nits — **Informational**

- `MandateUtilities.arrayifyBools` (`MandateUtilities.sol:72–89`) reads calldata by raw offset without checking `calldatasize()`; out-of-range reads return zero rather than reverting. Bounded by `numBools ≤ 1000`. Not reached by the Tier 0–2 mandates reviewed (they inline their own bounded `calldataload` with an explicit `length == n*32` check, e.g. `PeerSelect.sol:92`, `ElectionRegistry_Vote.sol:99`), but worth a `calldatasize` guard if it becomes reachable.
- `MandateUtilities.hexStringToBytes` (`:95`) computes `length/2 - 1`; an input shorter than 2 chars underflows and reverts (0.8 checked math) — a DoS on malformed input only.
- `ElectionRegistry_CreateVoteMandate.sol:96–98` calls `abi.encodeWithSelector(IPowers.adoptMandate.selector, initData, nonce, "…")` but `adoptMandate` takes a **single** argument (`IPowers.sol:107`). The extra encoded args are ignored by the ABI decoder — harmless, but misleading; drop them.

**Status:** Confirmed (source); no security impact.

### C-10 — Trust-model / centralization notes — **Informational**

- **`OpenAction`** (`OpenAction.sol:55`) and the `BespokeAction*` family forward caller-controlled calldata with "no check on decoded call data." Behind a privileged role this is intended power; behind `PUBLIC_ROLE` it hands the DAO to anyone. This is the single highest-leverage misconfiguration and should be flagged loudly in tooling/UX.
- **`MandateRegistry`** is `Ownable`; the owner can register/deactivate mandate addresses, but Powers only checks registry membership *at adoption* (`PowersUtilities.storeMandate:57–62`) — deactivating a mandate does not disable already-adopted instances. The `addressKey` mapping reflects only the most recent (name,version) registration (documented caveat, `MandateRegistry.sol:76–82`).
- **`PowersFactory`** and helper registries (`Nominees`, `ElectionRegistry`, `SlateRegistry`) are `Ownable`; correct operation depends on ownership being set to the intended party (the Powers instance for the helpers, a trusted curator for the factory/registry). Verify ownership wiring at deployment.

**Status:** Informational.

## 4. Positive observations

- **`fulfill` reentrancy ordering is correct.** `fulfilledAt` and `latestFulfillment` are set *before* the external call loop (`Powers.sol:376–381`), and the code comments explain why. A reentrant `request()` for the same action hits the `requestedAt > 0 || fulfilledAt > 0 → ActionAlreadyInitiated` guard (`:315`); a reentrant `request()` for a *different* mandate cannot read a stale throttle value because `latestFulfillment` is already updated. No reentrancy issue found.
- **Access control on state mutation is uniform:** every privileged setter is `onlyPowers`, and `fulfill` restricts the caller to the exact target mandate (`:358`). There is no post-constitute admin backdoor.
- **`PUBLIC_ROLE` + quorum is blocked at adoption** (`PowersUtilities.sol:53–55`), preventing meaningless/exploitable "everyone votes" configurations.
- **Duplicate-vote and duplicate-action guards** are present and correct (`hasVoted`, `ActionAlreadyInitiated`), and double-voting in `ElectionRegistry` is independently guarded by `hasVoted[electionId][voter]`.
- **Bounded execution:** `MAX_CALLDATA_LENGTH`, `MAX_RETURN_DATA_LENGTH`, `MAX_EXECUTIONS_LENGTH` cap the per-action work.

## 5. Recommendations summary

| Priority | Action |
|---|---|
| 1 | **C-01** — snapshot eligible-voter count at `voteStart`; use it as the quorum/threshold denominator. |
| 2 | **C-02 / C-04** — freeze the inputs a quorum-gated state-reading mandate depends on (nominee set, membership) for the action's lifetime, and/or default `maxExecutionDelay` to non-zero. |
| 3 | **C-03** — rank `DelegateTokenSelect` on `getPastVotes(nominee, snapshotBlock)`, not live `getVotes`. |
| 4 | **C-05** — let reform mandates carry full `Conditions`/`config` for adopted children, or curate the adoptable set. |
| 5 | **C-06 / C-07 / C-09** — document blacklist scope; add a `uint96` bound in `SafeAllowance_Transfer`; tidy decode/encoding nits. |
| 6 | **C-10** — treat mandate-to-role gating (esp. `OpenAction`) as the primary review target for every deployed org. |
