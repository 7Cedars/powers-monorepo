# Protocol Registry Governance — Governance Specification

> **Status:** Draft
> **Network:** Sepolia / Arb Sepolia / Opt Sepolia
> **Design date:** 2026-06-02

---

## Purpose

This organisation governs the `MandateRegistry` contract — the whitelist of approved mandate implementations for the Powers protocol. It decides which mandate contracts are registered, updated, or deactivated, and sets the criteria by which mandate proposals are evaluated. The Powers organisation is set as the `owner` of the deployed MandateRegistry, replacing a single-owner key with collective, role-based governance.

---

## Roles

| Role ID | Name | Description | How to join | Max members |
|---------|------|-------------|-------------|-------------|
| 0 | Admin | Founding team with elevated authority during the bootstrapping period. Holds a time-limited veto on mandate registrations. The Admin Veto mandate is intended to be revoked by a Developer vote approximately 6 months after deployment. | Assigned at deployment | 2 |
| type(uint256).max | Public | Everyone; no application needed | Automatic | Unlimited |
| 1 | Developer | Protocol developers who write, audit, and propose mandate implementations. Core voting body for registrations, reform, and criteria. | Appointed by Admin initially; thereafter by Developer peer vote | ~7 |
| 2 | SecurityCouncil | Security reviewers who must approve each registration before it can execute, and who hold emergency deactivation power. | Appointed by Admin initially; thereafter by Developer vote | ~3 |
| 3 | Community | Any account that has opted in to participate in governance. Can veto policy changes and vote to reactivate deactivated mandates. | Self-select (anyone) | ~50 |

## Governance Flows

### Flow 1: Register a Mandate

**Purpose:** Add a new mandate contract (or a new version of an existing mandate) to the registry so it becomes available for use in Powers constitutions.

**Steps:**

| Step | Mandate type | Who can call | Voting? | Conditions |
|------|-------------|--------------|---------|------------|
| 1 | StatementOfIntent | Developer | Yes — 50% quorum, 66% threshold, 7-day period | — |
| 2 | StatementOfIntent (approval) | SecurityCouncil | No vote — any council member can approve | Must come after step 1 passes |
| 3 | StatementOfIntent (veto) | Admin | No vote — any Admin can cast | Must come after step 1 passes |
| 4 | BespokeAction_Simple → `registerMandate()` | Developer | No | Must have step 2; must NOT have step 3; 14-day timelock from proposal |

**Rationale:** Mandate registration is a high-stakes, irreversible action that affects every organisation in the protocol ecosystem. A 7-day Developer vote ensures the proposing community has reviewed the submission. The Security Council's affirmative approval (step 2) acts as a required technical gate — if they do not approve, execution cannot proceed. The Admin veto (step 3) provides the founding team with an additional safety brake during the early protocol phase. The 14-day timelock (7 days longer than the voting period) gives both the Security Council and the Admin time to act after the vote passes.

**Why Security Council approval rather than a veto:** The protocol's condition system supports one `needNotFulfilled` per mandate. Since Admin holds the veto slot, the Security Council's check is implemented as a *required approval* — they must affirmatively sign off. A Security Council that sees a problem simply does not approve, blocking execution indefinitely until the proposal is withdrawn and resubmitted.

---

### Flow 2: Emergency Deactivate a Mandate

**Purpose:** Immediately deactivate a mandate that has a live security vulnerability or is otherwise unsafe, without waiting for a community vote.

**Steps:**

| Step | Mandate type | Who can call | Voting? | Conditions |
|------|-------------|--------------|---------|------------|
| 1 | BespokeAction_Simple → `deactivateMandate()` | SecurityCouncil | No — immediate execution | — |
| 2 | StatementOfIntent (reactivation proposal) | Community or Developer | Yes — 30% quorum, 51% threshold, 7-day period | — |
| 3 | BespokeAction_Simple → `reactivateMandate()` | Developer | No | Must have step 2; 2-day timelock |

**Rationale:** Emergency deactivation must be executable within hours. Requiring a community vote in a crisis would be counterproductive. The Security Council holds this authority precisely because it is a small, trusted body that can act quickly. The community reactivation path (steps 2–3) ensures the Security Council is accountable: any deactivation can be reversed by a community vote within ~9 days, providing a check on misuse of emergency powers.

This mirrors the "graduated accountability" principle from Carlisle & Gruby (2019, §4.1.5): emergency powers exist but are subject to reversal through a deliberative process. The Security Council can act, but cannot act permanently against community will.

---

### Flow 3: Set Submission Criteria

**Purpose:** Establish or update the criteria by which mandate proposals are evaluated (e.g., audit requirements, test coverage standards, documentation requirements).

**Steps:**

| Step | Mandate type | Who can call | Voting? | Conditions |
|------|-------------|--------------|---------|------------|
| 1 | StatementOfIntent (proposal) | Developer | Yes — 50% quorum, 66% threshold, 30-day period | — |
| 2 | StatementOfIntent (veto) | Community | Yes — 20% quorum, 51% threshold, 14-day period | Must come after step 1 passes |

**Rationale:** Criteria changes are slow-moving policy decisions that affect all future mandate submissions. A 30-day Developer deliberation period reflects the months timeline the organisation selected. The Community veto gives the broader membership a meaningful check on what standards are imposed on protocol contributors — this protects against Developers setting self-serving criteria.

**Limitation:** The `MandateRegistry` contract does not have a `setSubmissionCriteria()` function. This flow produces an on-chain governance record (the voted proposal) but does not write criteria data to any contract. Enforcement of criteria is social and reputational. A future governance reform could adopt a `SubmissionCriteriaRegistry` contract and add a bespoke execution mandate to write criteria on-chain.

---

### Flow 4: Governance Reform

**Purpose:** Add new mandates to this organisation's own constitution, allowing the governance structure to evolve.

**Steps:**

| Step | Mandate type | Who can call | Voting? | Conditions |
|------|-------------|--------------|---------|------------|
| 1 | StatementOfIntent (propose reform) | Developer | Yes — 66% quorum, 66% threshold, 14-day period | — |
| 2 | Adopt_Mandates | Developer | No | Must have step 1; 15-day timelock |

**Rationale:** Governance reform requires a supermajority (66% quorum and threshold) among Developers to prevent a minority from hijacking the constitution. The 15-day timelock (one day longer than the voting period) ensures there is time to review the proposed mandates after the vote passes. Following Hynes et al. (2020, Ch. 13): the reform mandate is the on-chain implementation of the "monitor, learn, review, adapt" step. An organisation without a reform path has no Step 7.

The broad `allowedRole` on the `Adopt_Mandates` execution mandate (Developers) rather than Admin-only reflects the OECD/IIASA cogeneration principle: adaptive capacity should not be concentrated in a single point of failure.

---

### Flow 5: Membership Management

**Purpose:** Allow accounts to join as Community members, and provide the founding team with the ability to appoint Developers and Security Council members during the bootstrapping period.

**Steps:**

| Step | Mandate type | Who can call | Voting? | Conditions |
|------|-------------|--------------|---------|------------|
| 1a | SelfSelect (role 3) | Public | No | — |
| 1b | BespokeAction_Simple → `assignRole(1, account)` | Admin | No | — |
| 1c | BespokeAction_Simple → `assignRole(2, account)` | Admin | No | — |
| 2a | RenounceRole (role 3) | Community | No | — |
| 2b | RenounceRole (role 1) | Developer | No | — |
| 2c | RenounceRole (role 2) | SecurityCouncil | No | — |

**Rationale:** Community membership is open (self-select) to keep participation accessible. Developer and Security Council appointment during the founding period is Admin-controlled for speed and pragmatism — the Carlisle & Gruby (2019, §4.1.2) warning about bootstrapping stalls applies here: if election of the first developers requires an existing developer vote, the organisation cannot start.

---

### Flow 6: Sunset Admin Authority

**Purpose:** Revoke the Admin Veto mandate approximately 6 months after deployment, transitioning the organisation from a founder-led structure to a fully peer-governed one.

**Steps:**

| Step | Mandate type | Who can call | Voting? | Conditions |
|------|-------------|--------------|---------|------------|
| 1 | StatementOfIntent (propose sunset) | Developer | Yes — 66% quorum, 66% threshold, 7-day period | — |
| 2 | BespokeAction_Simple → `revokeMandate(adminVetoId)` | Developer | No | Must have step 1; 8-day timelock |

**Rationale:** The founding team's authority is legitimate during the bootstrapping phase but should not be permanent. Rather than an on-chain timer (which the protocol does not support), this is implemented as a governance commitment: the Developer community agrees to call this flow at approximately the 6-month mark. The supermajority requirement ensures the founding team cannot block their own sunset — as a small minority (2 of ~62 voters), they cannot reach 66% opposition. This implements the Podger et al. (2020, Ch. 2) principle that formal grants of autonomy should be bounded by designed sunset mechanisms rather than relying on good-faith voluntary withdrawal.

**Note:** This mandate revokes the *Admin Veto mandate*, not the Admin role itself. After the sunset, Admin role holders retain their membership but have no governance mandates to exercise. Their role can be revoked separately by a future governance vote if desired.

## Checks and Balances

| Mechanism | How it works | Who holds it |
|-----------|-------------|--------------|
| Admin veto on registration | Admin can block any mandate registration within the 14-day timelock window | Admin (role 0), founding period only |
| Security Council approval gate | Registration cannot execute without explicit Security Council approval | SecurityCouncil (role 2) |
| Emergency deactivation | Security Council can deactivate any registered mandate immediately | SecurityCouncil (role 2) |
| Community reactivation | Any emergency deactivation can be reversed by a Community vote within ~9 days | Community (role 3) |
| Community veto on criteria | Developer criteria proposals can be blocked by Community majority | Community (role 3) |
| Governance reform supermajority | Constitution changes require 66% quorum and 66% threshold among Developers | Developer (role 1) |
| Timelock on registration | 14-day window between vote passing and execution | Automatic |
| Sunset mechanism | Admin veto mandate designed to be revoked ~6 months post-deployment | Developer (role 1) vote |

**Security considerations:**
- The Security Council is a single point of failure for registration: if all three members are unavailable or unresponsive, no registration can proceed. The organisation should plan for Security Council succession from the start.
- The Admin veto is a centralisation risk during the founding period. It is explicitly time-limited by governance commitment.
- The criteria flow produces no on-chain enforcement — criteria compliance is social only.
- Long `needFulfilled` chains (e.g., registration flow steps 1→2→4) create cascading stall risk if an intermediate step is never fulfilled. Per Hynes et al. (2020, Ch. 12): avoid chains longer than 3 sequential dependencies without a recovery path. The resubmission path (withdrawing and restarting an action) is always available.

## Design Rationale

This governance structure implements **polycentric authority** (Carlisle & Gruby, 2019) across four distinct roles with genuinely different mandate sets: Developers propose and execute; the Security Council gates and can deactivate; the Community checks and reverses; the Admin brakes during the founding period. Each role has *de facto* authority that differs from adjacent roles, not just a different label.

The registration flow in particular distributes the decision across three independent gatekeepers (Developer vote, Security Council approval, Admin non-veto), each acting on different timescales and with different institutional incentives. This redundancy reduces the probability of a bad mandate slipping through even if one gatekeeper fails, implementing the risk mitigation argument from Carlisle & Gruby (2019, §4.3).

The emergency deactivation path (Security Council acts fast, Community reverses slowly) reflects the **speed-legitimacy trade-off** discussed in Podger et al. (2020): legitimacy comes from deliberation, but deliberation takes time, and some decisions cannot wait. The solution is not to choose one over the other but to sequence them: fast unilateral action followed by slow collective review.

The 6-month Admin sunset reflects the **adaptive governance** principle from Hynes et al. (2020): governance structures should be designed to evolve. Starting with founder-led authority and transitioning to peer governance is a deliberate phase design, not a compromise. The sunset mechanism makes this transition legible and executable on-chain.

---

## Limitations

1. **No on-chain criteria enforcement.** The submission criteria flow produces a governance signal, not a data write. Criteria must be enforced by Developers and the Security Council when evaluating proposals.
2. **No automatic 6-month expiry.** The Admin veto sunset is a governance commitment, not an on-chain timer. The founding team could delay it if Developers do not call the sunset flow.
3. **Security Council stall risk.** If the Security Council does not approve a registration, the registration is permanently blocked for that action ID. The only remedy is for the proposer to start a new action.
4. **Single `needNotFulfilled` constraint.** The protocol supports only one blocking dependency per mandate. This forces the Security Council check to be implemented as a required approval rather than a veto, which changes the power dynamic slightly (inaction blocks rather than action blocks).
5. **No Developer election mechanism.** After the founding period, no mandate exists to elect or appoint new Developers. A future governance reform should adopt a `PeerSelect` or `Nominate + PeerSelect` flow for Developer membership.
